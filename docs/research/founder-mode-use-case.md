# Founder-Mode Use Case → Knowledge Graph Solutions

Source: `reference_repos/founder-mode-cancer/` (local, not redistributed) — a research compilation of Sid Sijbrandij's (GitLab co-founder) osteosarcoma treatment, documented across `overview.md`, `framework.md`, `ai-role.md`, `breakthroughs.md`, `systemic-barriers.md`, `source-code.md`, `future-vision.md`, and the `egri/founder-mode-pipeline` reference pipeline spec.

## 0. First question: what is the use case, precisely?

Not "help cancer patients" — that's too broad to design against. The actual sequence of events that worked for Sid, stripped to its mechanism:

1. **Standard genomic panels found nothing new after recurrence.** The known mutation profile was exhausted as an actionable lead.
2. **Non-obvious target discovery came from a different data modality** — single-cell RNA-seq of tumor tissue, not DNA sequencing, revealed FAP (fibroblast activation protein) overexpression. FAP is not a standard osteosarcoma biomarker; nothing in a mutation-only pipeline would have surfaced it.
3. **That target was then matched to an existing but unconventional modality** — FAP-targeted radioligand therapy (177Lu/225Ac-FAPi), a platform technology already validated for a *different* cancer (prostate, via PSMA), retargeted by swapping the ligand.
4. **Access was secured through a path most patients/physicians don't know exists** — FDA Individual Patient Expanded Access (Form 3926), approved in 48 hours. The real bottleneck was hospital IRBs, not the FDA.
5. **Multiple mechanistically-complementary therapies were layered in parallel**, not tried sequentially — checkpoint inhibitor + vaccine + oncolytic virus + NK cells + radioligand, each attacking a different part of the immune-evasion problem simultaneously.
6. **AI closed the information gap**, not by generating a diagnosis, but by doing literature synthesis, cross-referencing the specific mutation/expression profile against case reports, and structuring the decision (a documented "balanced scorecard": pillars, weights, scores) — always with a human expert team executing and validating.

**So the use case is:** *given a patient whose standard-of-care and standard genomic workup are exhausted, surface non-obvious druggable targets from whatever molecular data is available, find every modality (approved, off-label-platform, or expanded-access) that could plausibly hit those targets, map which of those modalities are mechanistically safe/complementary to combine in parallel, and show the access pathway and evidence for each option — all cited, all physician-reviewable, none of it hidden inside an LLM's prose.*

This is a substantially different and *narrower* problem than "build the whole founder-mode pipeline" (which includes wet-lab vaccine manufacturing, radioligand chemistry, and expanded-access paperwork — all out of scope for a knowledge-graph system). It's an information/reasoning problem, and it's exactly the shape of problem a knowledge graph is good at: multi-hop, structured, citable traversal across heterogeneous entity types that a pure vector-RAG system (or a generic ChatGPT session, which is literally what Sid used) handles poorly.

**This is also, directly, an extension of what this repo already set out to do.** SecondLook/Tier 1+2's existing framing — "second opinion for cases where standard-of-care has failed or the mutation is undocumented" — is the same trigger condition as Sid's recurrence. The gap is scope: our current Tier 1 (curated evidence retrieval) and Tier 2 (structural drug-binding prediction on a *known* mutation) both assume the actionable lead is already a validated missense mutation. Sid's actual breakthrough came from a completely different data modality (expression, not DNA) surfacing a target with no mutation involved at all. That's the real gap this founder-mode framing exposes.

## 1. What current SecondLook (Tier 1 + Tier 2) already covers vs. doesn't

| Founder-mode step | Covered today? | Gap |
|---|---|---|
| Documented evidence for a known mutation (Tier 1: CIViC/CTgov/CTRI/PubMed) | Designed, mostly built | None — this is standard-of-care-adjacent evidence lookup, already the right shape |
| Structural plausibility signal for an undocumented *missense* mutation (Tier 2) | Built and verified | Scoped to single amino-acid substitutions only, and to *drug-binding* mechanism specifically — doesn't touch expression-driven or non-mutational targets |
| Non-obvious target discovery from expression/pathway data (the actual FAP-discovery mechanism) | Not in scope anywhere | No expression-data ingestion path exists at all — this is the single biggest capability gap relative to the founder-mode use case |
| Modality-agnostic option surfacing (radioligand, oncolytic virus, NK-cell, gene therapy, CAR-T — not just small-molecule drugs) | Not in scope | Tier 2's candidate generation (DGIdb/Open Targets/ChEMBL) is entirely small-molecule/drug-centric; none of these five sources index radioligand conjugates, cell therapies, or oncolytic viruses as "candidates" |
| Expanded-access / regulatory-pathway knowledge (which modality has FDA 3926 precedent for which target class) | Not in scope, and not covered by any existing SecondLook data source | This is a genuinely novel, unstructured knowledge asset — nobody has built this as queryable data |
| Parallel-combination compatibility reasoning (which therapies are mechanistically complementary vs. redundant vs. risky together) | Not in scope | Requires a mechanism-of-action graph, not a flat evidence list |
| Balanced-scorecard decision support (structured, weighted, transparent) | Partially — `ui-flow.md`'s results screen shows evidence, but there's no explicit multi-criteria scorecard | Worth building deliberately *transparent* (see §4 below — this is exactly where RareCure's own scoring module failed methodologically, see `rarecure-build-reference.md` §4) |

## 2. Why FalkorDB / hybrid semantic+Cypher is the right shape for this

The founder-mode use case is fundamentally **multi-hop and heterogeneous**: target → modality-class → specific-agent → access-pathway → evidence, where each hop is a different entity type and the "right" path isn't known in advance (that's exactly what makes FAP a *non-obvious* target — nothing about osteosarcoma's standard biomarker list points there). A pure vector-RAG system retrieves *documents that sound relevant*; it doesn't traverse *structured relationships between entities*. Sid's own AI usage (ChatGPT literature synthesis) was exactly this limitation in practice — good at summarizing what it was pointed at, unable to do the structured "target X is hit by modality-class Y, which has FDA precedent Z, and is mechanistically complementary to therapy W already in the patient's plan" reasoning that actually drove the outcome.

FalkorDB specifically fits because it's a property graph with a **native vector index alongside Cypher** — so a single query can combine graph traversal (structured, auditable, "which nodes are N hops from this target via TARGETS/COMPLEMENTARY_TO/ACCESSIBLE_VIA edges") with semantic search (fuzzy, "find literature/case-report text similar to this expression signature or mechanism description") in the same retrieval pass, rather than running two separate systems and stitching results in application code. This is the standard "GraphRAG" pattern, and it maps directly onto the entity types below.

## 3. Solution menu — organized by which gap each one closes

Each item is independently implementable; none of them require the others to be useful. Ordered roughly by how directly they extend what's already built vs. how much new ground they break.

### 3a. Extends existing Tier 2 scope (lowest new-ground)

- **Expression-signature → target graph.** A node type for `ExpressionSignature` (e.g. "FAP overexpression in stromal-mimicking tumor cells") linked to `Target` nodes, populated from public differential-expression datasets (the same class of data the `egri` reference pipeline's `phase3_scrna.py` targets — GEO/TCGA scRNA-seq, not proprietary). This is the direct computational analog of the breakthrough that found FAP: given a patient's own expression data (if available) or a matched public cohort's, traverse from signature → target instead of only mutation → target. Directly extends Tier 2's "Step 0 scope gate" (currently missense-only) with a second, parallel entry point that doesn't require a mutation at all.
- **Target → modality-class edges, not just target → drug.** Reframe the `Target` node's outgoing edges to include modality *classes* (radioligand-conjugate, CAR-T, oncolytic-virus, checkpoint-inhibitor, neoantigen-vaccine — not just small-molecule), each with its own evidence requirements. This is a schema decision more than new data-source work, but it's the one that makes the graph modality-agnostic instead of drug-database-shaped like Tier 2's current candidate generation (Step 4, DGIdb/Open Targets/ChEMBL — all small-molecule-only).

### 3b. New graph-native capabilities (moderate new ground)

- **Platform-technology nodes.** A `PlatformTechnology` node (e.g. "mRNA neoantigen vaccine platform", "177Lu/225Ac radioligand platform") with an edge to any `Target` it could in principle be retargeted against, populated from the pattern documented in `future-vision.md` (177Lu-PSMA → retargeted to FAP by swapping the ligand, same isotope chemistry). This directly encodes the "swap the payload, keep the platform" reasoning that made Sid's radioligand and vaccine therapies possible — currently there is no data source anywhere in `data-sources.md` that captures this kind of cross-target platform reusability; it would need to be curated from FDA-approved-platform + published-retargeting-precedent literature, which is exactly a RAG-over-literature problem with a graph schema to structure the output into.
- **Expanded-access precedent graph.** A `RegulatoryPathway` node type (FDA 3926 precedent, by modality-class and indication) linked from `PlatformTechnology`/`Target` nodes. This is the single most novel, unstructured-elsewhere asset described in `systemic-barriers.md` and `breakthroughs.md` §6 — "every application approved within 48 hours" is itself the *finding*, not something any existing database tracks as queryable structured data. Building even a small, manually-curated seed of this (which modality classes have documented single-patient expanded-access precedent, for which target/indication combinations) would be a genuinely differentiated capability no existing tool offers, closing the "systemic barrier #6: information asymmetry" gap directly.
- **Mechanism-complementarity graph for parallel-combination reasoning.** `COMPLEMENTARY_TO` / `MECHANISTICALLY_REDUNDANT_WITH` / `KNOWN_INTERACTION_RISK` edges between modality-class nodes, seeded from mechanism-of-action metadata (checkpoint inhibitor = removes immune brake; vaccine = trains recognition; oncolytic virus = direct kill + antigen release — these are categorically different mechanisms, which is *why* they compounded in Sid's case). Cypher is a natural fit for "given this patient's already-selected therapies, traverse the graph for options that are complementary to what's already chosen and not redundant with it" — a query shape a flat evidence list can't express at all.

### 3c. Decision-support layer (built on top of the graph, not a data source itself)

- **Structured, transparent balanced-scorecard, not an LLM-generated composite score.** `ai-role.md` documents Sid's own process explicitly: pillars (efficacy, toxicity, availability, evidence quality) → weighted scores → decision. Build this as a literal feature — expose each option's scorecard dimensions as graph node properties (evidence level, access-pathway approval-time precedent, known toxicity signal, mechanism-class) and let the weighting be a disclosed, user-adjustable parameter, never a hidden LLM output. This is directly the lesson from `rarecure-build-reference.md` §4 (RareCure's scoring module hard-codes constants and calls the result "personalized," and its LLM-weight-generation step produces near-constant output while looking calibrated) — same failure mode to avoid here, and this repo's existing architecture rule ("LLM never states a fact it didn't retrieve or compute") already forbids it structurally. Worth stating as an explicit requirement before this gets built, not an implementation detail to discover later.
- **Citation-enforced, multi-hop synthesis.** The LLM synthesis layer's job here is exactly what it already is elsewhere in this project's architecture — organize the graph traversal's results into readable text, cite every claim to a specific node/edge/evidence item, never introduce a claim the graph traversal didn't produce. No new rule needed; this is the existing "no evidence, no claim" architecture rule extended to a richer entity/relationship structure.

### 3d. Explicitly out of scope for a knowledge-graph system

Worth naming so scope doesn't creep silently:

- Wet-lab vaccine/radioligand manufacturing, dosing, and clinical execution — that's a care-team/physician function, not software.
- Real-time ctDNA trend interpretation and treatment-response monitoring — this is a time-series/signal-processing problem, not a retrieval problem; a different subsystem, not this graph.
- Anything that would function as the actual decision-maker rather than decision-support — `ai-role.md`'s own "Limitations" section is explicit that AI augmented, never replaced, Sid's physician/advisory team; this project's existing disclaimer language (`tier2-structural-prediction.md` §10) already holds this line and should extend to whatever this graph surfaces too.

## 4. The question to resolve before naming anything

Given India-localization and hackathon-to-real-product scale constraints already established for this project, the founder-mode use case as documented is resource-intensive (Sid's approach involved 5+ sequencing providers, 8 scRNA-seq timepoints, concierge care coordination) — not directly replicable as "run the same protocol for everyone." The transferable part is the **reasoning infrastructure**, not the diagnostic volume: a graph that can do target-discovery-beyond-mutations, modality-agnostic option surfacing, and complementary-combination reasoning is valuable at whatever diagnostic-data volume a given patient actually has, including just a mutation and a cancer type (today's Tier 1/2 scope) on the low end, or expression data if available on the higher end.

**Open question, worth deciding explicitly rather than drifting into by default:** does v1 of the knowledge-graph layer target the *expression-signature → non-obvious-target* path (§3a, the actual FAP-discovery mechanism, requires expression data most patients won't have), or does it target the *modality-agnostic option surfacing + expanded-access precedent + combination reasoning* path (§3b/3c, valuable even for a patient who only has what Tier 1/2 already produce — a validated mutation and/or a structural plausibility signal)? The second path is buildable on top of what already exists without a new data-ingestion problem (no expression data required) and is closer to a natural Tier 3 extension of the current architecture; the first path is the more dramatic "founder mode" capability but depends on data most patients in this project's actual target population won't have.
