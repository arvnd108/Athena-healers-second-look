# RareCure → SecondLook: Build Reference

Source: `RareCure_Analysis_Report.md` (external static audit, commit `43494c7`, local-disk-only copy — not redistributed here) cross-referenced against this repo's own specs (`architecture.md`, `tier1-retrieval.md`, `tier2-structural-prediction.md`, `api-contracts.md`, `data-sources.md`, `validation-plan.md`, `ui-flow.md`, `../ISSUES.md`).

**Framing.** RareCure is not a working reference implementation to port from — it's a research prototype where two of six advertised modules are stubs, the headline metrics in its own paper don't reproduce from its own committed artifacts, and its core methodological claim (bounded weight clamping) is disproven by its own boundary test. Treat the report as two different kinds of input: (1) a small set of sound *patterns*, worth taking even though RareCure's own implementation of them is broken, and (2) a long, well-documented list of *specific failure modes*, each one directly checkable against a corresponding decision already made or still open in our own docs. The value here is mostly in category 2 — RareCure already ran into these mistakes and documented them precisely (file + line), so we don't have to discover them the hard way.

Where we've already made a decision that avoids one of these failure modes, this doc says so explicitly rather than only listing new work — knowing *why* a rule exists (because RareCure hit this exact bug) makes it easier to hold the line on that rule under time pressure later.

---

## 1. What to take as-is

Short list — most of RareCure's engineering is sound in isolation even where the surrounding system is broken.

- **Pydantic models as module contracts** (`models.py`, 8 enums + 14 models). The idea of typed dataclass/Pydantic boundaries between modules is good and matches our own `MutationValidationResult` / `AlphaMissenseResult` / `StructureResult` / `CandidateResult` / `BindingScore` pattern already built in Tier 2 — keep doing this for Tier 1's modules too.
- **Structured logging with `logger.exception`** in `rarecure/` (not `scripts/`, which uses bare `print()`). Module-scoped loggers, tracebacks on exception, `basicConfig` only at entry points — straightforward and worth matching.
- **Prompt sanitization against injection** (`llm_client.py:15`, `sanitize_for_prompt` strips odd characters, caps length before anything goes into an LLM prompt). Apply this at every point free-text (doctor's clinical question, patient-reported treatment history) enters a prompt.
- **`.gitignore` hygiene for secrets** — `.env`, `*.key`, `credentials.json` correctly excluded, no secret ever committed per the audit's `git log` check. Baseline, but worth confirming we match it.
- **Clean acyclic import graph** (`config → models → {modules} → pipeline`). No circular dependencies. Worth holding as an explicit constraint once Tier 1 + Tier 2 + orchestration all exist in the same place.

## 2. What to take and modify

Concept is sound; RareCure's implementation of it has a specific, named defect that must not be repeated.

## 3. What to build from scratch

RareCure either never implemented these, or has no equivalent at all.

- **The entire Tier 2 structural-prediction pipeline.** RareCure has no binding-affinity, structure-sourcing, or pathogenicity-scoring path of any kind — its "neoantigen" module (`neoantigen.py`) is a 23-line stub that always returns `candidates=[]`. This is not a gap to fill by adapting RareCure code; it's a capability RareCure never attempted, and it's this project's actual technical contribution. Already built and independently verified — see `../ISSUES.md` and the test suite.
- **Literature RAG, for real.** RareCure's Module 5 is the starkest gap in the whole report: every config parameter for the designed system exists (`RAGConfig`, 512-token chunks, `all-MiniLM-L6-v2`, ChromaDB, cosine ≥ 0.65, `TOP_K=5`) and **none of it is implemented** — the actual class is 8 lines that always returns `insufficient_evidence=True`. 0 of 47,719 output options carry a PMID. The README advertises "PMID-grounded" retrieval that produced zero PMIDs across the entire committed cohort. There is nothing to take from the code here — but the audit's own §5.4 prioritized recommendations are a genuinely useful build order for our `tier1-retrieval.md` §3 Literature RAG component, worth following roughly as written:
  1. Hybrid retrieval (BM25 + dense), not pure vector — gene symbols, variant notation (`p.V600E`), drug names, and NCT IDs are lexical tokens where semantic-only search underperforms.
  2. Chunk by abstract, not by fixed token count — one PubMed abstract = one chunk, `(pmid, title, journal, year, pub_type, mesh_terms)` as metadata, so every chunk is citable by construction.
  3. Enforce citation at the schema level: reject any evidence summary without ≥1 PMID that's verified to exist in the retrieved set — this is the strongest hallucination guardrail available for this domain, and it's a natural fit for our own "no evidence, no claim" rule already stated in `architecture.md` and `README.md`.
  4. Filter by publication type/recency (RCTs and systematic reviews weighted above case reports).
  5. A reranker over the fused top-k before the final top-5, given how costly one irrelevant retrieved abstract is in a medical setting.
  6. A ~50-pair ground-truth set (curatable from CIViC/OncoKB citations already being fetched) wired into an eval loop — without this, none of the above is tunable, and RareCure never built one.
- **Per-drug scoring signal.** RareCure's `score_drug` hard-codes `resp/safe/cost` as literal constants for *every* drug (`scoring.py:134-136`) — three of five scoring dimensions contribute nothing, so its "composite score" is a function of tier alone (all Tier-2 drugs score identically at `0.6375`). There's no real per-drug signal to take. If Tier 1 ends up needing any drug-level ranking beyond CIViC's own evidence level, that signal has to be built from actual source data (evidence strength from CIViC/evidence-level, not a constant), not adapted from RareCure.
- **Config-driven ontology/gene panels as data, not code.** RareCure's cancer ontology and gene panels are Python dict literals (`config.py:132-152`) despite the README promising YAML files that don't exist. Whatever cancer-type/gene scoping Tier 1's CIViC subset uses should be actual versioned config data from the start, not inline literals — this also makes the "which cancer types are in scope" decision auditable, which matters for the "explicit failure over silent fallback" principle below.

## 4. What to rethink and redesign

These are RareCure's methodological choices, not bugs — meaning the fix isn't "patch the code," it's "don't design it this way in the first place." Each one maps to a rule already stated in our own docs; this section is about confirming those rules are strict enough and staying disciplined about them once real time pressure hits.

- **Silent fallback that quietly defeats the product's own premise.** 260 of 261 RareCure patients fell back to a hard-coded common-gene panel instead of their own MAF-derived variants (only 1 patient's actual genome was ingested, and *that* patient got zero drug matches). The fallback is silently logged as a warning string, not surfaced as a distinguishable failure state, so 99.6% of the "personalized" cohort's drug matches trace to `CDK4 amplification` because `CDK4` is a literal string in a fallback gene list, not because of anything in the patient's tumor. This is the single most important thing to actively design against: **our own rule — "any module failure returns a structured error/low-confidence object, never a silent substitute" (`architecture.md`, and enforced throughout Tier 2's §8 exact-message table) — exists specifically to prevent this failure mode.** Concretely: nothing in Tier 1 or Tier 2 should ever substitute a generic/default value for a missing patient-specific input without that substitution being a first-class, visible field in the output — not a warning string a downstream reader has to `grep` for (RareCure's own analysis scripts had to reverse-engineer which patients were faked via `any("common" or "fallback" in w)` string-sniffing on log text, duplicated in two different scripts).
- **A metric that is claimed to be bounded but isn't.** RareCure's `clamp_weights` clamps each weight to a documented range, then renormalizes the whole vector to sum to 1 — which re-inflates the clamped value past its own ceiling (the README's own worked example: `safety=1.0` clamped against a `0.40` ceiling comes out at `0.7018`). The unit test doesn't catch it because the assertion threshold (`<= 0.85`) was set to accommodate the escape rather than catch it. The lesson isn't "clamp more carefully" — it's that **any output presented as a bounded/validated number needs a post-condition check in code (an assert, not just a test), and the test's threshold has to be the actual documented bound, not whatever the current buggy output happens to produce.** This applies directly to Tier 2's Step 6 (threshold labeling, `../src/secondlook/labeling.py`) — the label cutoff is explicitly meant to be an empirical, disclosed heuristic per `validation-plan.md`, which is already the right instinct (RareCure presents an undisclosed, methodologically-broken clamp as if it were principled); make sure the eventual implementation asserts the delta actually produces one of the three defined labels and never silently emits an out-of-range value the way the clamp does.
- **Ranking/scoring as an LLM output rather than a computed one.** RareCure's `generate_weights` asks an LLM for 5 scalar weights per patient, sampled 5× and taking the median — a plausible-sounding "AI-calibrated" design that, per the audit's own reproduction, produces only 2 distinct vectors across 261 patients (mean CV 0.004) while still being presented as personalized. This is worth rethinking at the design level, not just the implementation level: a scoring/ranking dimension that doesn't actually vary with the input shouldn't be computed by an LLM call at all — it should either be a fixed, documented constant (cheaper, equally honest) or a genuinely data-driven computation. Our own architecture already avoids this by keeping the LLM layer strictly downstream of computed evidence (`architecture.md`: "never introduces a claim absent from the evidence payload it received") — this is a case where the RareCure failure mode validates keeping that boundary strict rather than letting the LLM layer creep into scoring.
- **Live, uncached, non-versioned external calls presented as reproducible results.** RareCure fetches DGIdb/CIViC/OncoKB/CT.gov live at run time with no caching (beyond one unused `TTLCache`), no retrieval timestamp recorded anywhere in the output, and a paper claiming reproducible headline metrics that don't match its own committed `results/` artifacts (99.6% TAR / 0.38% BMR / 0 Tier-1 patients vs. the README's claimed 30.0% / 78.8% / non-zero). If any result is going to be quoted as a fixed number (a demo case, a validation-plan.md pass rate), it needs either a recorded snapshot (data version, retrieval date) or has to be explicitly labeled as "as of run time, may drift." This is already the instinct behind `tech-stack-setup.md`'s demo-case caching requirement and `validation-plan.md`'s "cite real accuracy figures, not assumed ones" rule — the RareCure report is the concrete demonstration of what happens when that discipline slips.
- **Diagnosis/cohort inclusion driven by unvalidated substring matching.** RareCure picks fallback gene panels via `k in patient.cancer_type.lower()` — `"malignant_fibrous_histiocytoma"` doesn't contain `"sarcoma"`, so it silently falls to a `default` panel that includes `NTRK1/2/3`, producing Larotrectinib as the top drug for 42 patients essentially by string-matching accident. Separately, the 261-patient "sarcoma cohort" actually includes ~20 non-sarcoma diagnoses (melanoma, basal-cell carcinoma, two benign fibromatoses) with no inclusion filter anywhere. **Never let a string-containment check drive clinical-facing logic.** Our own mutation validator already does exact, structured matching (parsed HGVS + residue-level comparison, not substring), which is the right posture — hold that same standard for any cancer-type/gene-panel/cohort-inclusion logic Tier 1 ends up needing, and validate diagnosis strings against an actual ontology rather than free-text matching.
- **Concurrency primitives scoped wider than a single request.** A module-level `asyncio.Semaphore` created at import time (`drug_match.py:90`) gets bound to whichever event loop first waits on it; since the pipeline calls `asyncio.run()` once per patient (a fresh loop each time), every subsequent patient's semaphore silently fails for ~two-thirds of its concurrent requests — invisible because the failures are caught by `return_exceptions=True` and merely logged. This didn't show up in RareCure's own committed run because the fallback-gene path never generated enough concurrent tasks to trigger it — it only fires "the moment the pipeline runs in its intended genomic mode... on more than one patient," i.e., exactly the real-world case the demo run never actually exercised. If Tier 1's CIViC/CTgov/PubMed fan-out (or any future async batch processing) uses shared rate-limiting/concurrency primitives, scope them per-request or to one long-lived loop for the whole run — never a bare module-level object that outlives a single `asyncio.run()` call.

## 6. Compliance note carried over unchanged

RareCure fetches OncoKB's `allAnnotatedVariants` with no license acknowledgment in an MIT-licensed repo, despite OncoKB requiring a commercial-use license — flagged in the audit as "external dependency, terms not verifiable from source" but a real risk as described. `data-sources.md`'s "Explicitly avoid depending on" table already excludes OncoKB (and DrugBank) for exactly this reason — no action needed, just confirming this was the right call independently of writing this document.
